Descrizione dell’iter di approvazione documentale
La sintassi ammessa per il versionamento dei documenti è la seguente:

     ●​ Y.X dove
            ○​ “Y” numero versione Major (da 0 a n)
            ○​ “.” separatore
            ○​ “X” numero versione Minor (da 0 a n)

Versione “Bozza” (v0.X)
Il documento è redatto all’interno del GDL di competenza, in questa fase il documento è in
versione bozza (0.X).

L’aggiornamento della versione bozza, al fine di tenere traccia delle modifiche, si ha
incrementando la prima variabile dopo il separatore (X).

Versione “Public Comment” (vY.0_PC) (OPZIONALE in base ai requisiti di progetto)
Successivamente, se il progetto per il quale il deliverable è stato prodotto richiede una fase
di public comment, il documento in formato PDF viene pubblicato su Drive e su Google
Group dedicati ai public comment. In questa fase la versione passa a (Y.0_PC) con Y=1 per
la prima versione del documento. Tutti gli stakeholder interessati possono lasciare un proprio
commento al documento pubblicato. I commenti saranno rilasciati seguendo delle specifiche
istruzioni, disponibili sul sito di Arsenàl.IT.

Durante il periodo di public comment, della durata di 14 gg, Arsenàl.IT analizzerà i commenti
rilasciati, proponendo una possibile soluzione. Ogni commento e la relativa risposta
rimarranno visibili all’intera comunità che potrà intervenire nella discussione.

Alla fine del periodo di public comment tutti i commenti analizzati da Arsenàl.IT verranno
sottoposti al GDL di competenza. In caso di approvazione i cambiamenti verranno integrati
nel documento di riferimento.

L’iter di pubblicazione e revisione si conclude nel momento in cui non sono apportati
cambiamenti sostanziali al documento secondo decisione del GDL di competenza.

Versione “Pubblica” (VY.0)
Una volta ottenuta una versione definitiva, essa andrà quindi in approvazione con le
seguenti modalità:

     ●​ se il documento deve essere inviato al cliente, la validazione è in carico al Dirigente
        dell’Area Tecnica;
     ●​ se il documento non deve essere inviato al cliente ma deve essere inoltrato ad un
        altro gruppo di lavoro interno ad Arsenàl (es. per la produzione di altra
        documentazione) l’approvazione deve avvenire da parte del Responsabile di Unità (o
        dell’Ufficio) produttore del documento.

Alla fine del periodo di public comment tutti i commenti analizzati da Arsenàl.IT verranno

Revisione Minor

nella discussione.

Alla fine del periodo di public comment tutti i commenti analizzati da Arsenàl.IT verranno

1.​ [RVE-121] GetAccessToken
1.1.​         Scopo
Questa transazione permette di ottenere un token JWT utilizzabile per l’accesso ad un
servizio.


1.2.​         Roles

 Actor:                       AccessTokenRequester


 Role:                        Invia la richiesta per ottenere un token di accesso JWT


 Actor:                       AccessTokenManager


 Role:                        Fornisce in risposta il token JWT



1.3.​         Standard di riferimento
 RFC2616                     IETF Hypertext Transfer Protocol - HTTP/1.1


 RFC4627                     The application/json Media Type for JavaScript Object Notation (JSON)


 RFC7519                     JSON Web Token (JWT)



1.4.​         GetAccessToken Request

1.4.1.​         Trigger Events
Questo messaggio viene inviato quando un AccessTokenRequester vuole accede ad un
servizio e deve ottenere dal AccessTokenManager un token JWT per l’accesso.

1.4.2.​         Message Semantics

Il messaggio GetAccessToken Request è una richiesta di tipo HTTP POST inviata dal client
al Server.

La chiamata è formattata in questo modo:

<scheme>://<authority>/<path>/AccessTokenManager
Dove:

     ●​ <scheme> deve essere di tipo http o https; in questo caso deve essere https;
     ●​ <authority> deve essere rappresentato come un host (indirizzo IP o DNS) seguito
        opzionalmente dalla porta;
     ●​ <path> può essere valorizzato con il percorso attraverso cui è possibile raggiungere
        il servizio.
     ●​ “AccessTokenManager” è una parte obbligatoria dell’URL che indica la risorsa che
        classifica il tipo di query;

Il Client deve precisare nel messaggio di richiesta il Content-Type Header = application/json.

1.4.2.1.​          Body

Il payload della richiesta dev’essere un JSON strutturato nel seguente modo:


Campo                                            Formato Descrizione


asserzione                                       string   Deve veicolare l’asserzione di identità SAML 2.0
                                                          codificata in base64.

                                                          Per le specifiche riguardanti l’asserzione di
                                                          identità fare riferimento alle specifiche di
                                                          sicurezza per il FSEr contenute all’interno del
                                                          documento: “Infrastruttura di sicurezza GDL-O
                                                          Sicurezza versione 1.0” (e successive).


patientId                                        string   Deve veicolare l’identificativo del paziente di tipo
                                                          token costituito da due parametri separati da un
                                                          pipe, ovvero strutturato [system]|[value] con:

                                                             ●​ system:     OID    del    MPI    regionale
                                                                (urn:oid:2.16.840.1.113883.2.9.2.50.4.1.2)
                                                                o                  del                  CF
                                                                (urn:oid:2.16.840.1.113883.2.9.4.3.2)
                                                             ●​ value: contiene l’MPI regionale o il CF del
                                                                paziente

1.4.3.​         Expected Action
AccessTokenManager verifica se i dati forniti permettono l’accesso ai vari servizi e se
l’asserzione di identità è valida. In caso positivo fornisce in risposta il token JWT.

Se il patientId in richiesta è valorizzato con il CF o MPI:
    ●​ Deve essere verificato che il valore di patientId in richiesta corrisponda al patientId
        dell’asserzione.
    ●​ La chiave per collegare token JWT e asserzione è il codice fiscale dell’utente.

L’asserzione deve essere poi salvata in modo da essere utilizzata per le successive
interazioni.




1.5.​         GetAccessToken response

1.5.1.​         Trigger Events
AccessTokenManager crea questo messaggio quando riceve e processa un messaggio di
tipo GetAccessToken Request.

1.5.2.​         Message Semantics

Se la richiesta effettuata non rispetta i requisiti identificati nel paragrafo 1.4.2 relativi
all’asserzione di identità (non valida), il SIO deve ritornare uno status code HTTP di risposta
uguale a 401 – Unauthorized e il body del messaggio vuoto. Il Content-Type associato alla
risposta dovrà essere text/html.

Se la richiesta effettuata non rispetta i requisiti identificati nel paragrafo 1.4.2 relativi ai
parametri (mancanti o valorizzati in modo errato), il SIO deve ritornare uno status code
HTTP di risposta uguale a 400 – Bad request e il body del messaggio vuoto. Il Content-Type
associato alla risposta dovrà essere text/html.

Se la query fornisce risultati, il SIO deve riportare lo status code HTTP della risposta pari a
200 – OK, il Content-Type associato alla risposta dovrà essere application/json e nel body
un JSON così strutturato:


Campo                                            Formato   Descrizione


jwt                                              string    Deve veicolare il token JWT.


esito                                            number    Deve veicolare l’esito dell’operazione.

                                                           Viene valorizzato con 0 se l’operazione è andata
                                                           a buon fine, 1 altrimenti


descrizioneEsito                                 string    Descrizione esito operazione.

jti                                              string    Id del token jwt. Deve coincidere con l’id
                                                           presente nell’asserzione d’identità in richiesta

                                                           dall’issuer presente nell’asserzione d’identità in
                                                           richiesta


sub                                              string    Deve essere valorizzato con il subject estratto
                                                           dal subject presente nell’asserzione d’identità in
                                                           richiesta


nbf                                              number    NotBefore: indica l’istante in UTC oltre il quale il
                                                           token JWT è valido. Deve essere valorizzato con
                                                           il numero di secondi da 1970-01-01T00:00:00Z
                                                           UTC.

1.5.3.4.​          Verifica del token JWT
Per effettuare la verifica del token devono essere eseguiti i seguenti passi:
   1.​ Estrazione del valore di base64(header) + “.” + base64(payload)
   2.​ Verifica della firma con la chiave pubblica
   3.​ Il token è quindi considerato valido se:
            a.​ La firma è valida
            b.​ L’ora di validazione è compresa tra nbf e exp
            c.​ Il servizio a cui si richiede l’accesso è compreso nella lista di aud

1.5.4.​         Expected action
Il client deve memorizzare il token JWT in caso di esito positivo o in caso di errore,
ricominciare la transazione dopo le correzioni, se necessarie.

2.​ [RVE-130] Chiamata Contesto
Le specifiche per questa transazione possono essere ampliate a seconda del servizio per
cui viene richiesto l’accesso, per il quale possono essere richieste maggiori specificità.


2.1.​         Scopo
Questa transazione viene effettuata per ottenere l’accesso ad un servizio, veicolando il
token JWT precedentemente richiesto con una transazione [RVE-121] GetAccessToken.


2.2.​         Roles

 Actor:                       Service Requester


 Role:                        Invia la query per ottenere l’accesso ad un servizio


 Actor:                       Service Manager


 Role:                        Riceve la query e fornisce le informazioni per usufruire del servizio per
                              cui è richiesto l’accesso




2.3.​         Standard di riferimento


 RFC2616                     IETF Hypertext Transfer Protocol - HTTP/1.1


 RFC4627                     The application/json Media Type for JavaScript Object Notation (JSON)


 RFC7519                     JSON Web Token (JWT)

2.4.1.​         Trigger Events
Questo messaggio di richiesta viene inviato dal Service Requester al Service Manager,
veicolando il token JWT ottenuto precedentemente da una transazione [RVE-121]
GetAccessToken, quando deve ottenere l’accesso ad un servizio.

2.4.2.​         Message Semantics

Il messaggio [RVE-130] Chiamata Contesto è una richiesta di tipo HTTP GET inviata dal
Service Requester al Service Manager.

La chiamata è formattata in questo modo:

<scheme>://<authority>/<path>/<resource>?<parametri>

Dove:

     ●​ <scheme> deve essere di tipo http o https; in questo caso deve essere https;
     ●​ <authority> deve essere rappresentato come un host (indirizzo IP o DNS) seguito
        opzionalmente dalla porta;
     ●​ <path> può essere valorizzato con il percorso attraverso cui è possibile raggiungere
        il servizio.
     ●​ <resource> è una parte obbligatoria dell’URL che indica la risorsa che classifica il
        tipo di query; viene definita specificatamente per il servizio a cui si vuole accedere
     ●​ <parametri>
             ○​ token: (obbligatorio) parametro NON ripetibile che veicola il JWT token
                 in base64 ottenuto precedentemente da una transazione [RVE-121]
                 GetAccessionToken;
             ○​ ulteriori parametri possono essere aggiunti specificatamente in
                 funzione del servizio per cui si richiede l’accesso.
     ●​ “&” deve essere indicata se vengono elencati più parametri;
     ●​ “,” deve essere indicata se vengono elencati più valori per lo stesso parametro.

Dev’essere effettuato l’URL encode della query string.

2.4.4.​         Expected Action
Il Service Manager che riceve questo messaggio deve analizzarne il contenuto secondo le
proprio capacità, compresa la verifica del JWT token, ed inviare un messaggio di risposta al
Service Requester, permettendo, in caso positivo, l’accesso al servizio richiesto.


2.5.​         [RVE-130] Chiamata Contesto response

2.5.1.​         Trigger Events
Dopo aver ricevuto ed analizzato il messaggio di richiesta, il Service Manager invia un
messaggio di risposta al Service Requester.

2.5.2.​         Message Semantics
Se la richiesta effettuata non rispetta i requisiti identificati nel paragrafo 2.4.2 e nel paragrafo
1.4.2 relativi al token JWT, il Service Manager deve ritornare uno status code HTTP di
risposta uguale a 401 – Unauthorized.

Se la richiesta effettuata non rispetta i requisiti identificati nel paragrafo 2.4.2 relativi ai
parametri, considerando anche i parametri aggiuntivi che possono essere aggiunti per far
fronte alle specificità del servizio, il Service Manager deve ritornare uno status code HTTP di
risposta uguale a 400 – Bad request.

Se la query fornisce risultati, il Service Manager deve riportare lo status code HTTP della
risposta pari a 200 – OK e la pagina HTML a cui accedere al servizio.

2.5.3.​         Expected Action
Il Service Requester deve recepire le informazioni contenute nel messaggio di risposta:
    ●​ se di esito negativo, deve analizzarne gli errori ed effettuare una nuova transazione
        dopo aver corretto il messaggio di richiesta, se necessario;
    ●​ se di esito positivo, può utilizzare il servizio per cui ha ottenuto l’accesso.
